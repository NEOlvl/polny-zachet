# ТЗ: Mini App «Полный зачёт» (черновик)

Веб-интерфейс чек-листа внутри Telegram (Telegram Mini App). Дополняет бота, не заменяет его: кнопочный интерфейс работает как раньше, все требования `SPEC.md` остаются в силе.

Статус документа: **принято владельцем 22.11.2026**. Открытые решения в конце зафиксированы по рекомендациям; детальные требования к поведению переносятся в `SPEC.md` задачами из `FIXES.md`.

## Цель

Тот же личный чек-лист, но с удобным экраном: категории, пункты с отметками одним касанием, карточка пункта, прогресс, поиск. Нужен, когда кнопочный интерфейс становится тесным (сотни пунктов).

Критерий успеха: пользователь открывает Mini App из бота, видит свой прогресс, отмечает пункт, закрывает — отметка видна и в боте, и при следующем открытии Mini App.

## Что входит в MVP

- Список категорий с счётчиками `сделано/всего` и процентом.
- Список пунктов категории с отметками; отметка ставится и снимается касанием.
- Карточка пункта: название, категория, статус, `description`, `hint`, `tips`, фото.
- Общий прогресс и прогресс по категориям.
- Поиск по названию и подсказке (те же правила, что `/find` в боте: без регистра, «ё» = «е», все слова запроса).
- Авторизация только через подпись `initData` Telegram — отдельной регистрации и входа нет.

## Чего в MVP НЕТ

Не делать и не закладывать «на будущее»:

- Интерактивная карта, фильтры сверх «только неотмеченные» (сам фильтр — в открытых решениях).
- Кнопка «Поделиться» и генерация share-картинки (в боте уже есть; для Mini App — отдельное решение ниже).
- Кнопка «Ошибка в пункте» (остаётся в боте).
- Настройки уведомлений, `/delete_me`, любые админ-функции.
- Открытие Mini App вне Telegram (десктоп-браузер без Telegram — только режим разработки).
- Оплата, подписки, несколько языков — как и в боте.

## Архитектура

Рекомендуемый вариант (см. открытые решения): **один процесс** — бот и веб-сервер живут в одном контейнере и одном asyncio-цикле.

```
Telegram ──long polling──► aiogram-бот ─┐
                                        ├─► общая SQLite (data/bot.db)
Telegram ──HTTPS──► Caddy ──► FastAPI ──┘        общий контент (content/*.yaml)
                          (uvicorn в том же процессе)
```

- **FastAPI** поднимается в `app.main` рядом с `dp.start_polling` (uvicorn внутри того же event loop). Порт — настройка `MINIAPP_PORT` (по умолчанию 8000); без `MINIAPP_URL` веб-часть не стартует, бот работает как раньше.
- **База общая** — тот же `data/bot.db`, те же модели `users`/`progress`, тот же `ProgressService`. Отметка из Mini App и из бота — одна запись, синхронизация не нужна (см. открытые решения).
- **Контент общий** — тот же `ContentHolder`: `/reload` в боте сразу виден и Mini App, логика `spoiler`, `hint`, `description` одна.
- **Фронт** — статические файлы `web/` (`index.html`, `app.js`, `style.css`), отдаёт FastAPI из того же контейнера. Подключается `telegram-web-app.js`, тема берётся из CSS-переменных Telegram.
- **HTTPS** — Caddy (отдельный сервис в compose) с автоматическим Let's Encrypt проксирует домен на порт FastAPI. Домен и DNS — шаг владельца.

Вход в Mini App: кнопка `web_app` «Открыть чек-лист» на главном экране бота (рядом с «Чек-лист») — появляется только когда задан `MINIAPP_URL`. Кнопка в BotFather (Menu Button) — опционально, владельцу.

## Авторизация

Все запросы `/api/*` требуют заголовок `Authorization: tma <initData>` (сырая строка `window.Telegram.WebApp.initData`).

Проверка на сервере:

1. Разобрать `initData` как query string, вынуть `hash`.
2. Собрать data-check-string: пары `key=value` кроме `hash`, отсортированные по ключу, через `\n`.
3. `secret = HMAC_SHA256(key="WebAppData", msg=BOT_TOKEN)`.
4. `HMAC_SHA256(key=secret, msg=data_check_string)` в hex равен `hash` — иначе 401.
5. `auth_date` не старше 24 часов — иначе 401.
6. Из поля `user` (JSON) берём `id` и `username` — это `tg_id` пользователя. Доверять ничему другому из `initData` нельзя.

Дальше тот же `touch_user`: пользователь создаётся при первом обращении (новому прописывается `source` = `miniapp`, чтобы в `/stats` было видно тех, кто пришёл сразу через приложение), `last_seen` обновляется на каждый запрос — для статистики Mini App считается обычной активностью.

Подделать `initData` без токена бота нельзя; токен на клиент не отдаётся.

## API

Черновой набор (финальные имена зафиксируем в первой задаче реализации). Все ответы — JSON, все пути под `/api`.

| Метод и путь | Что отдаёт |
|---|---|
| `GET /api/summary` | общий `done/total/percent` и по каждой категории: `id`, `title`, `done`, `total` |
| `GET /api/categories/{id}` | категория и её пункты: `id`, `title`, `done`, `spoiler`, `has_details` |
| `GET /api/items/{id}` | карточка: `title`, категория, `done`, `hint`, `description`, `tips`, `has_photo`, `spoiler` |
| `POST /api/items/{id}/toggle` | переключить отметку, вернуть новое `done` |
| `GET /api/items/{id}/photo` | картинка пункта (см. ниже), 404 если фото нет |
| `GET /api/search?q=…` | до 8 результатов как в боте: `id`, `title`, `done`, категория |

Правила повторяют бота:

- проценты считаются только по пунктам текущего контента (`ProgressService.summary`);
- `toggle` по несуществующему id — 404;
- поиск не находит неотмеченные спойлеры (как `/find`);
- запрос поиска в логи не пишется.

## Фото пунктов

`photo` в контенте — Telegram `file_id`, его нельзя отдать браузеру напрямую, а ссылка `api.telegram.org/file/bot<token>/…` раскрыла бы токен. Поэтому `GET /api/items/{id}/photo` работает проксием:

1. `getFile` по `file_id` → `file_path` (кэшируем в памяти, путь живёт ~час);
2. сервер скачивает файл с `api.telegram.org` и стримит клиенту с правильным `Content-Type`.

Скачивание — через `aiohttp` (уже зависимость aiogram), новых зависимостей не надо. Сами картинки можно кэшировать по `file_id` в `data/photo_cache/`, чтобы не тянуть Telegram на каждый запрос — решаем в задаче по объёму.

## Спойлеры

Поведение бота сохраняем по духу: пункт со `spoiler: true` в списке показывается «Скрыто — нажми, чтобы открыть», первое касание раскрывает название, второе открывает карточку. Раскрытые id живут только в памяти страницы (sessionStorage) — после перезапуска Mini App неотмеченные спойлеры снова скрыты, это допустимо так же, как в боте. Отмеченный спойлер всегда с названием.

## Развёртывание

- Тот же VPS, тот же `docker compose`: сервис `bot` дополнительно публикует порт Mini App, новый сервис `caddy` (образ `caddy:2`, `Caddyfile` в репозитории) слушает 80/443 и проксирует на `bot:8000`.
- Новые настройки `.env`: `MINIAPP_URL` (например `https://checklist.example.com`), `MINIAPP_PORT`. Без `MINIAPP_URL` веб-часть выключена — бот и backup работают как сейчас.
- Шаги владельца: купить домен, DNS A-запись на сервер, вписать `MINIAPP_URL`, `scripts/deploy.sh`. Сертификат Caddy получает сам.
- Бэкапы не меняются: база та же, контент тот же. В `data/photo_cache` (если будет) бэкап не нужен.

## Тесты

- Проверка подписи `initData`: валидная строка принимается, неверный `hash`/старый `auth_date`/отсутствие заголовка — 401. Тестовую подпись генерируем в тесте тем же алгоритмом с фиктивным токеном.
- API на тестовом контенте и временной базе: `summary`, список пунктов с отметками, `toggle` туда-обратно, поиск, спойлеры в выдаче, 404 на чужой/несуществующий пункт.
- Клиент — `httpx` + `ASGITransport` (добавляем `fastapi`, `uvicorn`, `httpx` в `requirements.txt`; `httpx` нужен только тестам и проксированию фото, если выберем его вместо aiohttp).
- Прогон стандартный: `.venv\Scripts\python -m pytest` и `ruff check .` зелёные.

## Разработка без VPS

- Локально: `uvicorn` + polling бота в одном процессе, как на сервере; страницу можно открыть в обычном браузере.
- Для разработки — необязательный режим `DEV_TG_ID=<id>`: если задан, авторизация `initData` пропускается и запросы считаются от этого пользователя. Только локально: в проде переменной нет, её наличие пишется в лог при старте.
- Для проверки внутри настоящего Telegram без VPS — туннель до локального порта (`cloudflared` или `ngrok`), полученный `https://`-адрес в `MINIAPP_URL` и в BotFather (`/myapps` → Edit → URL). Это шаг владельца.

## Открытые решения — зафиксировано 22.11.2026

Принято по рекомендациям ниже: SQLite, один процесс, фронт без сборщика, спойлеры и фильтр в MVP, share-картинка — нет, синхронизация через общую базу, разработка локально с `DEV_TG_ID` + туннель для приёмки. Таблицы оставлены как обоснование.

### 1. База: остаться на SQLite или переходить на PostgreSQL — **принято: SQLite**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **SQLite (рекомендую)** | Если веб и бот в одном процессе — писатель всё равно один, конфликтов нет. Ноль работ по миграции, бэкапы и `/export` не меняются | При разделении процессов позже — вероятные `database is locked`; WAL + busy_timeout снимают часть риска, но не всё |
| PostgreSQL | Снимает вопрос навсегда, путь к росту (этап 5 IDEAS) | +сервис, +миграция данных, +зависимость `asyncpg`, усложнение бэкапов и `/export`; при одном процессе — избыточно |

**Рекомендация:** SQLite. В одном процессе гонок нет; переезд на Postgres — отдельная задача, когда появится отдельный сервис или нагрузка. Страховка в MVP — включить WAL и `busy_timeout` на соединении (несколько строк).

### 2. Mini App в том же контейнере или отдельный сервис в compose — **принято: один процесс**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Тот же процесс (рекомендую)** | Общие `ContentHolder` и `ProgressService`: `/reload`, спойлеры, отметки синхронны бесплатно; SQLite остаётся валидным выбором; один контейнер, deploy как сейчас | Сбой веба может уронить бота и наоборот (митигация: uvicorn под тем же supervisor — исключения в хендлерах FastAPI процесс не роняют) |
| Отдельный сервис | Изоляция, можно рестартовать веб без бота | Второй писатель в SQLite → почти точно нужен Postgres; `/reload` бота надо как-то транслировать в веб (mtime-наблюдение); больше движущихся частей |

**Рекомендация:** один процесс. Меньше кода, нет проблемы синхронизации, Postgres не нужен.

### 3. Фронт: один HTML/JS-файл или сборщик — **принято: статики без сборщика**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Простые статики, без сборщика (рекомендую)** | `index.html` + `app.js` + `style.css`, ноль тулчейна, правится как обычный файл, отдаётся FastAPI | При росте UI рано или поздно захочется компонентов — но это этап «карта/платформа», не сейчас |
| Vite + фреймворк | Удобнее при сложном UI | Node-инструментарий, сборка в Docker, оверкилл для трёх экранов |

**Рекомендация:** без сборщика, ванильный JS. IDEAS прямо разрешает оба пути — берём простой.

### 4. Спойлеры и share-картинка в MVP — **принято: спойлеры и фильтр в MVP, share-картинки нет**

| Вопрос | Варианты | Рекомендация |
|---|---|---|
| Спойлеры | а) как в боте — скрыты, раскрытие касанием, состояние в памяти страницы; б) в MVP вообще не показывать неотмеченные спойлеры; в) показывать сразу | **а)** — дёшево (флаг уже приходит из API) и не ломает привычную механику |
| Share-картинка | а) не входит в MVP; б) кнопка «Поделиться» на экране прогресса с той же Pillow-генерацией | **а)** — генерация уже есть в боте, дублировать в вебе незачем; добавим позже, если попросят |
| Фильтр «только неотмеченные» | а) в MVP (переключатель над списком, состояние только на клиенте); б) после MVP | **а)** — тривиально на клиенте и это главная причина появления Mini App при сотнях пунктов |

### 5. Синхронизация отметок бот ↔ Mini App — **принято: общая база, протокола нет**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Общая база без протокола (рекомендую)** | Отметка — одна запись в `progress`; бот и веб читают одно и то же, расхождений нет в принципе. Экран в боте показывает актуальное при следующей отрисовке | Открытое старое сообщение в боте не перерисуется само — то же поведение, что сегодня при «Список обновился» |
| Push-уведомление бота о клике в вебе | Мгновенная реакция в открытом чате | Нужен канал веб→бот ради редкого кейса — избыточно |

**Рекомендация:** общая база, никакой синхронизации. Это прямое следствие решения №2 (один процесс).

### 6. Как разрабатывать и показывать без VPS — **принято: локально с DEV_TG_ID + туннель для приёмки**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Локальный прогон + `DEV_TG_ID` (рекомендую)** | Полный прогон: страница в браузере, реальная база `data/bot.db`, API отвечает. Скриншоты владельцу без Telegram | Не проверяет настоящий initData и верстку внутри Telegram |
| Туннель (`cloudflared`/`ngrok`) + BotFather | Настоящий Mini App в настоящем Telegram на домашнем ПК | Каждый перезапуск туннеля (бесплатный ngrok) меняет домен — надо править в BotFather |
| Сразу VPS + домен | Продовая проверка | VPS ещё не арендован — блокирует старт работы |

**Рекомендация:** основной путь — локальный прогон с `DEV_TG_ID`; для финальной приёмки перед выкладкой — туннель (или подождать VPS, который и так в планах первым шагом).

## Что нужно от владельца (не код)

- Домен и DNS-запись на сервер (для прода; для разработки не нужно).
- VPS — уже в шагах STATUS.md; Mini App без него на прод не выложить.
- В BotFather при выкладке: привязать Web App URL к боту (`/myapps`), при желании — Menu Button.
